### 2026-08-30: 0.19.1 release gate (turso cold-build fix, every offered store gated)

Full battery, `node benchmark/release.mjs` (compare + 13k/26k scale + stress + both quality
evals, then every non-default store's tree battery), Apple Silicon (M4 Pro, 14 logical cores),
Node 26.7.0, still on 0.19.0's number per RELEASING.md step 2; the 0.19.1 bump happens after
this sitting. One continuous invocation, no split runs.

**First sitting to gate every store the schema offers.** `release.mjs` now reads `store`'s enum
straight from `schema.json`, so after the default store's full gate (sqlite: compare, 13k/26k
scale, stress, both quality evals) it runs the hub/13k/26k/stress tree battery again for each
other offered store. Every prior sitting measured sqlite only; this is the first report with
duckdb and turso numbers at the 13k and 26k scale corpora.

#### What this sitting gates

Per CHANGELOG.md's 0.19.1 entry, two fixes:

- **turso's cold build was quadratic.** It maintained its full-text index on every inserted row,
  so indexing cost grew with what was already indexed. A 13k tree could not finish at all before
  this fix. The fix writes rows first and builds the index once afterward, inside the same
  transaction: the 6,566-note hub corpus went from 945,411 ms to 3,350 ms to index, and the
  index on disk from 61.5 MB to 27 MB. Incremental edits are unchanged.
- **A race on a tree with no index yet.** Two `sense` commands starting at the same moment could
  fail with `database is locked` or `duplicate column name`: the busy timeout was applied after
  the WAL conversion it needed to cover, and schema setup and frontmatter column discovery both
  read the column list before the write transaction that then altered it. Commands on an
  existing index were unaffected.

The turso tree-battery numbers below are the direct evidence for the first fix: a 13k and a
26k turso tree that previously could not finish now complete, at times faster than duckdb's.

**The headline: turso completes at every scale, and now beats duckdb doing it.** Before this
release's fix, turso's cold build was quadratic and a 13k tree did not finish; here it completes
13k in 87.6s and 26k in 164.6s. turso is faster than duckdb on the hub battery (48.1s vs 67.0s)
and at 13k (87.6s vs 115.8s), and its cold-crawl wall time is lower than duckdb's at every size
measured (hub, 13k, 26k, and stress).

**duckdb's stress numbers are the one thing here that reads as a concern, not a regression.**
Cold crawl (42.5s), `map` (3121 ms), and both bulk-change rows (11.7s / 10.8s) are far above
sqlite's and turso's numbers on the same 2,000-note, 300-field corpus, and above duckdb's own
hub/13k/26k rows scaled linearly. There is no prior duckdb stress column to compare against
(first sitting), so RELEASING.md step 4's "moved beyond noise" test does not apply; nothing here
is reported as a regression. It is reported because a shape cliff duckdb has not been gated
against before is exactly what this corpus exists to catch, and this is the first time duckdb
has run against it at release-gate scale.

#### Limitation: the release comparison never crosses the embed path for sqlite

`compare.mjs` builds its corpora with `embed: false` (`benchmark/lib/corpus.mjs:139`), so the
sqlite before/after table above never exercises the embed or vector path there. The duckdb/turso
tree batteries above run through `benchmark/run.mjs`'s own corpus build instead, which is why
they carry `semantic_find_ms` numbers sqlite's compare table lacks; the two are not the same
harness path and are reported separately for that reason (see the store-battery section above).
