### 2026-08-30: 0.20.0 release gate (comment leak fix, builder-owned write path)

Full battery, `node benchmark/release.mjs` (compare + 13k/26k scale + stress + both quality
evals, then every non-default store's tree battery), Apple Silicon (M4 Pro, 14 logical cores),
Node 26.7.0, still on 0.19.2's number per RELEASING.md step 2; the 0.20.0 bump happens after
this sitting. One continuous invocation, no split runs. The 0.19.2 gate is the prior column
for every table below.

#### What this sitting gates

Per CHANGELOG.md's 0.20.0 entry, plus the write-path proof that only a capture gate can show:

- **Hidden comment text no longer leaks into the index.** A `%%...%%` comment split by a blank
  line, and an inline `<!-- -->` comment opened in one paragraph and closed in a later one,
  were indexed with their markers while Obsidian hides them. Text extraction now resolves
  sibling blocks in one pass with code held out of it, so a `%%` inside a fenced block stays
  literal. All three cache schema versions move (sqlite 18 to 19, duckdb 2 to 3, turso 3 to
  4), so an existing tree rebuilds on its first query after the upgrade.
- **The write path is `Builder`'s; `Store` answers queries only.** `Store` loses
  `reconcile()`. Bringing the index current is internal to the package: `Builder.build()` owns
  it, and `openStoreForWatch` hands it to the one caller that reconciles repeatedly,
  `src/watch.ts`. Owner decision 2026-08-30: it stays internal, no root exports; a consumer
  that needs the index current runs any query, since every query reconciles first.
- **`sense watch` reuses one parse worker pool** across its whole lifetime instead of paying
  85-100 ms of pool startup on every tick.
- **An embed model change that only moves its resolved identity is adopted in meta in place
  on duckdb and turso**, which previously cleared the cache and re-embedded every chunk. The
  behaviour was sqlite-only before.
- **A config change that forces a rebuild names which config segment moved**, on all three
  stores instead of reporting a generic rebuild reason.

The config version did not move (5, unchanged) and neither did the chunk version (chunk:v5).

#### Write path: store-dump gate

`benchmark/store-dump.mjs` is the refactor gate for anything touching the write path, and this
release grows it from two scenarios (cold, incremental) to six, adding four reopen scenarios
(warm, schema-bump, signature, embed-identity) that also capture the store's stderr notices.
Several `open()` branches (full rebuild versus in-place adoption) end at identical tables by
different routes, and the notice is the only observable that tells them apart.

- The six-scenario A/B (cold and incremental captured under both v0.19.2 and the working
  tree, all six under the working tree) ran on the refactor branch before handover and
  reported no unexpected diffs; the shipped tree (d536684) differs from that verified state
  only in `package-lock.json`.
- `embed-identity` is the observable for this release's duckdb/turso change: 0.19.2 cleared
  the cache and re-embedded every chunk on an identity-only embed-model change, 0.20.0 adopts
  the new identity in meta in place, and `notices.txt` separates the two routes.
- This sitting re-ran the `schema-bump` scenario on all three stores: a cold build, a
  schema-version mismatch written into meta, a reopen that prints
  `sense: cache format changed (new sensemaking version); rebuilding the index` as its only
  notice, and rebuilt tables plus ranked search output byte-identical to the cold capture for
  every store (130,603 table rows each).
- The battery's nfcorpus and fever legs corroborate against real prior cache state: both
  printed the rebuild notice against caches written by 0.19.2-era code. That is the
  formalized cache-rebuild sanity check observed against actual old cache state, not
  fabricated meta.

#### Scratch-tree verification

Both versioned-format paths verified on a scratch tree against the packed build, per

- A `sense.config.json` at the oldest supported version (1) auto-migrates: `node bin/cli.js

#### Limitation: the release comparison never crosses the embed path for sqlite

`compare.mjs` builds its corpora with `embed: false` (`benchmark/lib/corpus.mjs:139`), so the
sqlite before/after table above never exercised the embed or vector path there beyond the
`embed cold build` row. The duckdb/turso tree batteries above run through
`benchmark/run.mjs`'s own corpus build instead, which is why they carry `semantic_find_ms`
numbers the rest of sqlite's compare table lacks; the two are not the same harness path and
are reported separately for that reason (see the store-battery section above).
