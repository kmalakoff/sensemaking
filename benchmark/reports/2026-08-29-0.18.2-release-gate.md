# 0.18.2 release gate: parallel parse

The parse stage dispatches to a worker pool above 200 files. Everything else is
unchanged, and the tables below are mostly here to show that.

## Hub corpus, 0.18.1 (npm) vs this working tree

| metric | 0.18.1 | 0.18.2 |
|---|---|---|
| cold crawl (wall) | 7102 ms | **2504 ms** |
| warm query (`COUNT(*)`) | 149 ms | 139 ms |
| BM25 search (canonical join) | 150 ms | 139 ms |
| lexical `search` (BM25 + link fusion) | 196 ms | 193 ms |
| `search` row size (json) | ~71 tokens | ~71 tokens |
| `map` (orient) | 170 ms / ~496 tokens | 170 ms / ~496 tokens |
| `peek` largest note (~77274 t) | 150 ms / ~581 tokens | 151 ms / ~581 tokens |
| bulk change (500 files): first query | 1094 ms | **648 ms** |
| bulk change (500 files): warm watcher | 140 ms | 143 ms |
| in-process: cold index build | 5985 ms | **2351 ms** |
| in-process: freshness check, no change | 40.1 ms | 46.5 ms |
| in-process: update, 1 file touched | 42.6 ms | 55.2 ms |
| in-process: update, 10 files modified | 49.4 ms | 50.6 ms |

Cold crawl is 2.84x, the in-process build 2.55x. A bulk sync of 500 changed
files crosses the same 200-file threshold, which is why that row moves too.

**The two rows that rose are noise, and the reason is that they measure the same
thing.** Touching one file's mtime adds no measurable work on a 6,566-file tree:
the cost either way is the freshness scan over every file. Re-measured on this
tree with 15 repeats each rather than the harness's median of 3 to 5, both land
together: freshness 51.8 ms (50.8-56.6), update-1 51.7 ms (50.1-54.5). The
sitting's own numbers disagree internally, freshness +16% against update-1 +30%,
while update-10, a strictly larger operation, moved +2%. A real per-invocation
regression would move all three by the same absolute amount. The built
`reparse.js` also loads tinypool only inside the pooled branch, so nothing extra
runs on this path. Per-invocation cost is P8's subject in
cold-build-performance.md; these rows are not evidence for it.

## Scale and stress

| corpus | store | cold crawl | in-process build | update 1 | update 10 |
|---|---|---|---|---|---|
| hub 6.5k | sqlite | 2504 ms | 2351 ms | 55.2 ms | 50.6 ms |
| 13k | sqlite | 6159 ms | 4687 ms | 105.4 ms | 114.8 ms |
| 26k | sqlite | 8396 ms | 7811 ms | 203.2 ms | 206.1 ms |
| stress | sqlite | 6957 ms | 6725 ms | 284.3 ms | 439 ms |
| hub 6.5k | duckdb | 6045 ms | 4398 ms | 62.6 ms | 74.4 ms |
| 13k | duckdb | 13002 ms | 8422 ms | 107.8 ms | 121.3 ms |
| 26k | duckdb | 26192 ms | 18281 ms | 200.1 ms | 217.8 ms |
| stress | duckdb | 42883 ms | 36867 ms | 284.3 ms | 439 ms |

The 26k row was 25.93 s at the previous sitting and is 8.40 s here, so pooling
holds at 4x the hub corpus rather than degrading. That was the open question
going in: every threading measurement before this one was taken on the 6,566
file tree alone.

DuckDB stays roughly 2.4x slower than sqlite on a cold build and the gap widens
with size. The parse saving underneath is identical, because parse is
store-agnostic; the difference is duckdb's non-parse write path, which scales
with file count. That is Amdahl, filed in cold-build-performance.md, and P0b
exists to break it into stages. It is not a threading result and should not be
read as one.

The stress corpus's 9534 ms raw-SQL BM25 row is the documented
unguarded-by-design cliff (the canonical query calls `snippet()` directly), not
a regression.

## Output parity, serial against pooled

Separately from this sitting, a serial-forced and a pooled-forced cold build of
the hub corpus were compared on both stores at n=5 per cell. Document order,
warning text and order, parse-error count, frontmatter column order and the
top-3 BM25 hits are byte-identical. Speedups there: sqlite 5944 -> 2014 ms
(2.95x), duckdb 9782 -> 5919 ms (1.65x), spreads 0.8-6.4%.
