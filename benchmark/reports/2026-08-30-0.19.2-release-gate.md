### 2026-08-30: 0.19.2 release gate (one reconcile orchestration, duckdb field-stats chunked)

Full battery, `node benchmark/release.mjs` (compare + 13k/26k scale + stress + both quality
evals, then every non-default store's tree battery), Apple Silicon (M4 Pro, 14 logical cores),
Node 26.7.0, still on 0.19.1's number per RELEASING.md step 2; the 0.19.2 bump happens after
this sitting. One continuous invocation, no split runs. This is the second sitting to gate
every store the schema offers; the 0.19.1 gate is the prior column for every table below.

#### What this sitting gates

Per CHANGELOG.md's 0.19.2 entry, plus one refactor proven only by this sitting's before/after
tables:

- **One reconcile orchestration, not three.** `src/store/reconcile.ts` now runs one algorithm
  for sqlite, duckdb, and turso, parameterised by a `ReconcileDialect` (begin mode, column limit,
  ALTER-type suffix, and a `reconcileContent` hook each store still owns). Net -276 lines across
  the three per-store forks it replaces. `benchmark/store-dump.mjs` is the proof: table dumps
  plus ranked search output with scores, verified byte-identical per store on cold and
  incremental passes, so a lexical index living outside the logical tables can't hide a ranking
  change a plain table dump would miss.
- **duckdb's field-stats scan no longer runs one wide query.** It issued one query per `map`
  command carrying a `string_agg(DISTINCT variant_typeof(...))` aggregate per frontmatter column,
  and duckdb degrades superlinearly in the number of such aggregates in a single projection. The
  scan now runs in chunks of 16 aggregates.
- **`CAPABILITY_NAMES` joins the exported `Capability` type**, naming a sixth capability,
  `sql-functions`: whether an engine can register `has`/`basename`/`segment` as SQL functions,
  which turso's client cannot. The gap itself is unchanged; it is now a named capability instead
  of a hand-written store list.

No schema version moved (sqlite 18, duckdb 2, turso 3, all unchanged) and no config version
moved.

**One real movement, and it is unexplained.** In-process cold index build went 1991 to 2971 ms,
+49%. This is the row most exposed to this release's reconcile rewrite: it measures the same
reconcile path that collapsed from three per-store implementations into one orchestration over
`ReconcileDialect` this sitting gates. Two things sit against reading this as a plain consequence
of that rewrite. Wall cold crawl moved the other way, 2536 to 2445 ms. Both bulk-change rows
improved substantially, 1015 to 619 ms (first query) and 161 to 136 ms (with warm watcher), and
that same reconcile code runs underneath bulk change too. No mechanism reconciles a slower
in-process cold build with a faster bulk change against the same rewrite, and none is proposed
here.

RELEASING.md's test for a real regression is that it moves consistently and grows with tree size,
which is what the 13k and 26k rows exist for. This row does not. In-process cold build at 13k went
3513 to 3335 ms, down 5.1%, and at 26k 7069 to 7637 ms, up 8.0%, against +49% at hub scale. Those
two are cross-sitting readings with no baseline column of their own, so they carry less weight than
the hub row's within-sitting pair. For a genuine 49% cold-build cost to hide at 13k, though, the
drift there would have to run about 36% the other way in the same sitting.

**How much a single reading is worth, measured.** The baseline column re-installs the published
package, so the same npm artifact has now been measured in two sittings:

| 0.19.1 npm package | in the 0.19.1 sitting | as this sitting's baseline | |
|---|---|---|---|
| in-process cold index build | 1642 ms | 1991 ms | +21% |
| cold crawl (wall) | 2103 ms | 2536 ms | +21% |
| bulk change (500 files): first query | 588 ms | 1015 ms | +73% |

Identical code, so all three deltas are sitting-to-sitting spread rather than cost. This corrects
the bulk-change reading above: local's 619 ms is in line with the 588 ms that same package recorded
in its own sitting, so that row is the baseline reading high, not the rewrite running faster. It
does not dispose of the +49%, which is a within-sitting pair measured under one set of conditions,
but it is the reason the hub cold-build row is carried into the plan for a second reading rather
than treated as a settled 49% cost.

Everything else in the compare table is flat or better, and every token count is unchanged
(`search` row ~71 tokens, `map` ~496 tokens, `peek` ~581 tokens at 0.8% of the largest note).
`embed cold build` is a new row since the 0.19.1 gate, added to `compare.mjs` itself; it has no
prior template column, and both of its own columns come from this run: 12137 to 12209 ms, inside
noise.

#### Limitation: the release comparison never crosses the embed path for sqlite

`compare.mjs` builds its corpora with `embed: false` (`benchmark/lib/corpus.mjs:139`), so the
sqlite before/after table above never exercised the embed or vector path there until this
sitting's new `embed cold build` row. The duckdb/turso tree batteries above run through
`benchmark/run.mjs`'s own corpus build instead, which is why they carry `semantic_find_ms`
numbers the rest of sqlite's compare table lacks; the two are not the same harness path and are
reported separately for that reason (see the store-battery section above).
